# 1. Мотивация

Мониторинг нужен, чтобы:

1. Остановить потери заказов и контрактов
   Мы должны видеть: где именно рвётся жизненный цикл заказа (статус, очередь, воркер, БД), и реагировать до того, как клиент пожалуется.
2. Снизить время расследования инцидентов  
   Сейчас без метрик и алертов инциденты живут вслепую: проблемы обнаруживаются поздно, диагностика ручная, релизы задерживаются.
3. Управлять масштабированием на фактах  
   Нагрузка растёт; без измерений невозможно доказать, что масштабировать и когда.
4. Ввести SLA/SLO по заказам и по API-партнёрам  
   Появился B2B: нужен контроль квот, RPS, ошибок, задержек, чтобы сохранить доверие и избежать завала заказами.

Ожидаемый бизнес-эффект:

- меньше просрочек и потерянных заказов;
- меньше штрафов, возвратов, арбитража;
- повышение удержания B2B-партнёров;
- предсказуемые расходы на инфраструктуру - масштабирование по метрикам, а не на глаз.

# 2. Выбор подхода к мониторингу

## API-сервисы (Shop API, CRM API, MES API) - RED

Для API выбран RED-подход, так как:
- API являются основными точками входа ценности;
- бизнесу важно понимать, принимает ли система заказы и с какой скоростью;
- деградация API напрямую сказывается на клиентах и партнёрах;
- RED-метрики сопоставимы с SLA.

Особый фокус сделан на MES API, поскольку он является узким местом системы и напрямую влияет на сроки производства.

## Инфраструктура и базы данных - USE

Для инфраструктурных компонентов (EC2, PostgreSQL, RabbitMQ) выбран USE-подход, так как:
- система развернута в единичных инстансах и чувствительна к исчерпанию ресурсов;
- большинство инцидентов проявляются сначала как насыщение ресурса, а не как ошибки;
- USE-метрики позволяют заранее выявлять деградацию и планировать масштабирование.

USE даёт техническую основу для решений о вертикальном и горизонтальном масштабировании.

## Сквозной процесс заказа - Четыре золотых сигнала + бизнес-метрики

Для жизненного цикла заказа выбраны "Четыре золотых сигнала" в сочетании с бизнес-метриками, так как:
- техническая доступность сервисов не гарантирует корректную обработку заказов;
- ключевая бизнес-проблема - заказы, застрявшие в статусах без ошибок;
- необходимо контролировать SLA по времени обработки заказа, а не только состояние сервисов.

Этот уровень мониторинга связывает технические инциденты с финансовыми и репутационными потерями.

# 3. Метрики и ярлыки

## RabbitMQ

### 1. Number of dead-letter-exchange letters in RabbitMQ
- Зачем: прямой индикатор того, что сообщения падают из-за ошибки обработки, TTL, неправильной маршрутизация.
- Ярлыки: `vhost`, `exchange`, `queue`, `routing_key`, `reason` (если доступно), `env`.

### 2. Number of message in flight in RabbitMQ
- Зачем: показывает в работе/не подтверждено, помогает ловить зависания консьюмеров.
- Ярлыки: `queue`, `consumer_group`, `consumer_tag` (ограниченно), `env`.

### 3. Дополнительно
- Глубина очереди и age of oldest message по очередям заказов/статусов/расчётов как ранний сигнал, что система перестала успевать обрабатывать поток.

## Shop API

### 1. Number of requests (RPS) for internet shop API
- Зачем: базовая нагрузка, тренды, корреляция с ростом заказов.
- Ярлыки: `route` (шаблон пути), `method`, `status` (2xx/4xx/5xx), `env`.

### 2. Number of requests (RPS) per user for internet shop API
- Зачем: обнаружение аномалий (боты, пики, злоупотребление).
- Ярлыки: `client_type` (b2c/b2b/anonymous), `api_key_id` (если партнёры).

### 3. Response time (latency) for shop API
- Зачем: влияет на конверсию и UX; помогает увидеть деградации БД или внешних зависимостей.
- Ярлыки: `route`, `method`, `status_class`, `env`.

### .4. Number of HTTP 200 for shop API / Number of HTTP 500 for shop API
- Зачем: быстрые индикаторы качества; 5xx - вина на нашей стороне, повод для инцидента.
- Ярлыки: `route`, `env`, `exception`.

### 5. CPU % for shop API / Memory Utilisation for shop API
- Зачем: выявить сатурацию инстанса.
- Ярлыки: `instance_id`, `env`.

### 6. Number of simultanious sessions for shop API
- Зачем: индикатор конкурентности; полезно для планирования масштабирования.
- Ярлыки: `instance_id`, `env`.

### 7. Kb tranferred (received) for shop API / Kb provided (sent) for shop API
- Зачем: сетевые пики, стоимость трафика, эффект от загрузки 3D-файлов.
- Ярлыки: `instance_id`, `env`.

## CRM API

### 1. Number of requests (RPS) for CRM API
- Зачем: нагрузка от продавцов + фоновые процессы статусов и закрытия заказов.
- Ярлыки: `route`, `method`, `status_class`, `role`, `env`.

### 2. Response time (latency) for CRM API
- Зачем: скорость подтверждения `MANUFACTURING_APPROVED` и закрытия `CLOSED`.
- Ярлыки: `route`, `role`, `status_class`, `env`.

### 3. Number of HTTP 500 for CRM API
- Зачем: прямой сигнал, что CRM перестала корректно подтверждать или закрывать заказы.
- Ярлыки: `route`, `env`.

### 4. CPU % for CRM API / Memory Utilisation for CRM API
- Зачем: saturation инстанса при росте числа продавцов/объёма заказов.
- Ярлыки: `instance_id`, `env`.

## MES API

### 1. Number of requests (RPS) for MES API
- Зачем: отражает нагрузку от операторов и от интеграций/расчётов.
- Ярлыки: `route`, `method`, `status_class`, `client_type`, `env`.

### 2. Number of requests (RPS) per user for MES API
- Зачем: детект всплески запросов от UI или партнёра; база для квот, rate limiting и backpressure.
- Ярлыки: `client_type`, `api_key_id`.

### 3. Response time (latency) for MES API
- Зачем: база для изучения проблемы замедления MES, особенно по эндпоинтам дашборда и расчёта.
- Ярлыки: `route`, `client_type`, `status_class`, `env`.

### 4. Number of HTTP 500 for MES API
- Зачем: прямой сигнал деградации ядра и вероятной потери заказов, статусов.
- Ярлыки: `route`, `client_type`, `env`.

### 5. CPU % for MES API / Memory Utilisation for MES API
- Зачем: подтвердить упор в ресурсы и обосновать вынос вычислений/масштабирование.
- Ярлыки: `instance_id`, `env`.

### 6. Number of simultanious sessions for MES API
- Зачем: реальная конкуренция операторов и API-клиентов.
- Ярлыки: `client_type`, `env`.

### 7. Kb tranferred (received) for MES API / Kb provided (sent) for MES API
- Зачем: сетевые пики.
- Ярлыки: `instance_id`, `env`.

## PostgreSQL

### 1. Memory Utilisation for shop db instance / Memory Utilisation for MES db instance
- Зачем: индикатор нагрузки на БД и риска роста latency.
- Ярлыки: `db=shop|mes`, `instance_id`, `env`.

### 2. Number of connections for shop db instance / Number of connections for MES db instance
- Зачем: частая причина деградации - исчерпание пула ведёт к росту latency и ошибкам.
- Ярлыки: `db`, `env`.

### 3. Size of shop db instance / Size of MES db instance
- Зачем: рост данных ведёт к росту времени запросов, индексов, backup-ов, отслеживаем оставшееся место на диске.
- Ярлыки: `db`, `env`.

## S3 storage

### 1. Size of S3 storage
- Зачем: прогнозирование стоимости и лимитов; сигнал утечек, если не удаляем временные файлы или дубликаты.
- Ярлыки: `bucket`, `file_type`, `env`.

## Сквозные бизнес-метрики

### 1. Время в статусе: `order_time_in_status_seconds{status=...}`
- Зачем: видеть, где заказ застревает (PRICE_CALCULATED, MANUFACTURING_APPROVED, MANUFACTURING_STARTED, SHIPPED, CLOSED).

### 2. Застрявшие заказы: `orders_stuck_total{status=..., threshold="3d|7d|14d"}`  
- Зачем: ранняя реакция на застрявшие заказы без жалоб клиентов.

# План действий

## Этап 0 - экстренные меры
1. Включить базовые метрики VM/managed DB средствами облака (CPU/MEM/DISK/NET).
2. Зафиксировать критичные очереди RabbitMQ и текущие параметры retry/DLQ.

## Этап 1 - платформа метрик и алертов
1. Создать инстанс метрик Prometheus.
2. Развернуть Grafana и настроить доступы (RBAC).
3. Подключить экспортеры: node_exporter, postgres_exporter, rabbitmq_exporter.
4. Сделать дашборды RED на API и USE - инфраструктура.
5. Настроить алерты, каналы оповещения и правила.

## Этап 2 - логи и трассировка (2–6 недель, параллельно)
1. Централизованное логирование - ELK.
2. Корреляция по `trace_id`; `order_id` хранить в логах/трейсах.
3. Внедрение OpenTelemetry + Jaeger.
4. Сквозной мониторинг заказа - путь одного и всех заказов через систему от начала до конца (по времени/ошибкам на этапах).

## Этап 3 - прикладные и бизнес-метрики
1. Внедрить метрики API сервисов: RPS, latency, 5xx, срезы по route.
2. Добавить метрики задач расчёта стоимости - очередь, длительность, ошибки.
3. Добавить бизнес-метрики статусов заказа - time-in-status, stuck.
4. Ввести метрики по API-партнёров - api_key_id, квоты, аномалии, без персональных ярлыков.


### Этап 4 - эксплуатация (постоянно)
1. Калибровка порогов алертов и SLO.
2. Регламент: on-call, постмортемы, еженедельный обзор метрик.
3. Связь с roadmap: алерты → задачи оптимизации/масштабирования.

## Показатели насыщенности

### 1. Сервисы (Shop/CRM/MES)
- `CPU`: warning >70% (10 мин), critical >85% (5 мин)  
- `Memory`: warning >75% (10 мин), critical >90% (5 мин)

Что должно происходить при превышении:
1. алерт в канал инцидентов + автоматический тикет;
2. диагностика: топ эндпоинтов по latency/5xx;
3. временные меры: rate limiting для B2B, отключение тяжёлых операций, вертикальное масштабирование инстанса;
4. если повторяется - задача на оптимизацию/масштабирование.

### 2. RabbitMQ
- `DLQ letters`: warning >0, critical рост >10/мин  
- `Oldest message age`: warning >5 мин, critical >15 мин  

Что должно происходить:
1. проверка консьюмеров, корректировка retry/DLQ; 
2. увеличение воркеров/инстансов (если возможно);
3. разделение очередей (heavy vs light), настройка prefetch.

### 3. PostgreSQL
- `Connections`: warning >70% max_connections (10 мин), critical >85% (5 мин)
- `Disk`: warning >75%, critical >90%
- `Memory`: warning >75%, critical >90%

Что должно происходить:
1. Алерт в канал инцидентов + автоматический тикет; 
2. Настройка пулов соединений (при необходимости - pgbouncer), 
3. Оптимизация запросов или индексов (особенно для MES дашборда), 
4. Увеличение диска, архивация, партиционирование, 
5. При появлении реплик: вывод чтения дашбордов на read-replica.
